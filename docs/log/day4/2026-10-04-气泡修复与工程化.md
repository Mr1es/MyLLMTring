# Day 4：修 bug + 工程化整改

今天干的事有点杂，但都是被逼出来的。

## 1. 桌宠不出气泡 —— 排查了一整天

昨晚桌宠一直没冒气泡，shim 日志却干干净净，**服务端完全看不到报错**，
只有 Cortico 那边显示工具状态是 `NOT_EXECUTED_STREAM_ABORTED`。

结果排查出**三层独立的原因**，修掉一个还有一个：

1. **跑的是旧代码进程** —— 改了代码但旧进程还占着 8787 端口在监听
2. **控制台选中的不是本地 provider** —— `qwen3-8b` 存在但没选中，桌宠实际在用云端 `ds`，shim 根本没被调用
3. **SSE 协议踩坑（真凶）** —— 这个最阴，反复排查才发现

第3 点值得单独记一下。Cortico 校验工具参数时要求：
`output_item.added` 的 `arguments` 必须是**真空串**，
之后所有 delta 顺序拼接起来要**严格等于** done 里的全量值。

而我当时为了让 `arguments` 是合法 JSON，写的是 `JSON.stringify({script: ''})`，
实际发出去的是 `'{"script":""}'` —— 起手就带了内容。
于是拼接结果变成 `{"script":""}{"script":"你好"}`，跟 done 对不上，
上游直接判定流异常中断，工具永不执行。**而 shim 自己完全不知道发生了什么。**

修复就是把起手和发参数拆成两个函数，起手必须是 `''`。

中间还走错了两次路：我一直以为「input 里有 `function_call_output`」
或「最后一项是 `function_call_output`」就是工具结果回合，
其实都不对。**用户输入藏在 `external_event_frame` 的 `function_call_output` 里**，
判断该不该说话要看**最后一个 `function_call 的 name`**。

*排查到凌晨的时候最崩溃的时刻，是发现 shim 日志一行错都没有 —— 干净得让人绝望。*
*后来想明白了：它只是老实发了自己以为合法的东西，怪不了它。*

## 3. 工程化整改（按六条标准）

要求是：模块化封装、主程序只做组装、按功能组织文件层级、
代码顶部写注释、前后端解耦、根目录和每个功能目录都要有 README。

原来的 `shim/server.js` 是 **319 行单文件**，所有职责混在一起。
拆成了：

```
shim/
├─ index.js      组装层：读配置 → 建服务 → 挂路由 → listen（无协议逻辑）
├─ config.js     配置集中 + 零依赖读 .env
├─ routes/       models / responses 两条路由
├─ protocol/     SSE 事件对象构造 + 六事件序列写出
├─ core/         decide() 判断该不该说话、input 解析（纯函数，可单测）
└─ clients/      Dify 客户端，闭包持有 conversation_id
```

顺手做了个严肃批评报告 `docs/REVIEW.md`，列了技术债和"如果只做三件事"。

## 4. 踩的两个环境坑

**pnpm 起不来**：pnpm 10+ 会自管理版本，`packageManager` 声明的版本和本机不一致时，
它去解析旧版本失败，导致**连 `pnpm --version` 都报错**。
corepack、环境变量、代理方案全试过都没用，最后直接把声明改成和本机一致的版本。

**AI 启动的常驻进程会被回收**：用会话后台任务起的 shim，
跑了 **11 小时 54 分**后进程消失，日志无任何报错 —— 不是崩溃，是被会话生命周期回收。
需要常驻的进程必须用 `start-pet.bat` 的 `start /min` 起独立进程。

## 5. 还有个自己发现的：启动脚本每次必等 30 秒

截图里看到 `[5/6] Waiting for the pet console` 每次都卡很久，
一查发现是**脚本顺序写反了** —— 它在等 17788 端口，
但那个端口是 `pnpm dev` 启动之后才监听的。
等于「先等一个还没被启动的服务」，必然等满 30 秒。

改成后台并行探测后，那段固定空等没有了。
这个是**用户直觉发现**的，不是测试报出来的，
说明「每次都慢」这种确定性现象，比偶发bug 更值得当场深挖。
